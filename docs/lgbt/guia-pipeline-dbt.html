01O modelo mental do dbt

Antes de qualquer detalhe, a ideia central.

dbt é a camada de transformação. Ele não extrai dado e não carrega dado de fora — isso é a ingestão (Python). O dbt pega o que já está no banco em estado bruto e vira, só com SELECT, as tabelas que a aplicação vai usar.

Três ideias bastam para entender tudo que foi feito:

  • Um modelo é um arquivo .sql com um SELECT. O dbt embrulha esse SELECT num CREATE VIEW ou CREATE TABLE e roda no banco. O nome do arquivo vira o nome da tabela/view. Sem INSERT, sem UPDATE, sem DDL na mão.
  • Modelos referenciam outros modelos com {{ ref('nome') }}. Disso o dbt monta sozinho o grafo de dependências (DAG) e descobre a ordem de execução. Você nunca escreve "roda A antes de B".
  • O mesmo SQL serve de documentação e de teste. Um teste é um SELECT que não pode devolver linhas; se devolver, falhou.

O resto — camadas, macros, tags, seeds — é organização em cima desses três pilares.

As três camadas do dbt (staging → intermediate → marts) são a convenção padrão da comunidade. A regra de ouro: cada camada só lê a anterior. Um mart nunca lê raw direto; um staging nunca faz conta de indicador.

03Etapa 0 — Ingestão não é dbt

ingestion/ingest.py — Python puro com pandas + SQLAlchemy.

Responsabilidade única: ler toda aba de toda planilha e gravar no schema raw, sem nenhuma transformação de negócio. Descoberta automática — não há mapeamento manual de aba para tabela.

O que ele faz

  • Varre ingestion/input/lgbt/<ano>/*.xlsx.
  • Para cada aba, cria raw.<prefixo>_<planilha>_<aba> — ex.: raw.lgbt_perfil_pns_est_reg_civil_total_casamentos_uf.
    • <prefixo> = lgbt (do config do tema).
    • <planilha> = abreviação curta do nome do arquivo (mapa prefixos_planilha em ingestion/temas/lgbt_config.yml).
    • <aba> = nome inteiro da aba, só normalizado (sem acento, snake_case) — nunca abreviado.
  • Nomes de coluna são normalizados e truncados em 55 caracteres.
  • Drop-and-reload: cada execução recria as tabelas do zero. Não há histórico de linhas.
  • O histórico das execuções fica em raw.etl_importacao_arquivos (arquivo, aba, tabela, nº de linhas, data).
# joga os .xlsx do ciclo aqui
ingestion/input/lgbt/2026/

# roda (recria todo o schema raw)
python ingestion/ingest.py --tema lgbt --ano 2026

# só ver os nomes de tabela que sairiam, sem gravar
python ingestion/ingest.py --tema lgbt --ano 2026 --dry-run

Por que separar

A ingestão é "burra" de propósito. Se a planilha muda de formato, o conserto é num lugar só (aqui ou nos identifier dos sources). Toda regra que exige entender o relatório vive no dbt, versionada e testada.

O dbt_project.yml, na parte que importa

models:
  observadh:
    staging:       { +materialized: view,  +schema: staging }
    intermediate:  { +materialized: view,  +schema: intermediate }
    marts:         { +materialized: table, +schema: marts }
      lgbt:
        +tags: ["lgbt"]        # permite rodar só o tema: --select tag:lgbt

staging e intermediate são view (baratas, sempre refletem o raw mais recente, fáceis de depurar). marts é table (é o que a aplicação lê — precisa ser rápido).

05Conceitos-chave do dbt

Os sete que aparecem o tempo todo neste projeto.

{{ source(...) }} — a porta de entrada

Referencia uma tabela que o dbt não criou (as raw). Declarada em _lgbt__sources.yml. Cada entrada tem name (apelido estável usado nos modelos) e identifier (o nome real no banco, que muda a cada carga se a aba mudar de nome).

sources:
  - name: raw_lgbt
    schema: raw
    tables:
      - name: raw_lgbt_total_casamentos_uf          # apelido estável
        identifier: lgbt_perfil_pns_est_reg_civil_total_casamentos_uf  # nome real

{{ ref('outro_modelo') }} — a cola entre modelos

Referencia outro modelo dbt pelo nome do arquivo (sem .sql). O dbt substitui pelo nome real da tabela/view e registra a dependência. É isso que constrói o DAG.

Materialização — view ou table

viewtable

Ocupa disco?nãosim

Jinja + macros

Todo .sql do dbt passa por um pré-processador de template (Jinja). O que está entre {{ }} é código que gera SQL. Uma macro é uma função que devolve um pedaço de SQL — como uma função no Excel, mas para texto de query.

Tags

Rótulo em um modelo. Todos os modelos do tema têm tag:lgbt, então dbt build --select tag:lgbt roda só o tema (os temas antigos PSR/PI/PCD vão conviver no mesmo projeto).

Seeds

CSV versionado no repo que o dbt carrega como tabela (dbt seed). Para dados de referência pequenos e estáveis — aqui, o de-para de código IBGE ↔ nome de município/UF.

Testes

Dois tipos. De schema (declarados em YAML: not_null, unique, accepted_values…). Singulares (um arquivo .sql em tests/ que devolve as linhas problemáticas — zero linhas = passou).

06Camada 1 — Staging

models/staging/lgbt/stg_lgbt_*.sql — uma por tabela raw consumida.

Trabalho do staging, e só isso:

  • ler uma tabela raw via {{ source() }};
  • renomear colunas para nomes estáveis e legíveis;
  • converter tipo (::int, ::bigint, ::numeric) — no raw quase tudo é texto ou double;
  • limpeza mecânica (trim, padronizar rótulo, tratar "-" como 0).

Nunca junta duas fontes, nunca calcula percentual, nunca agrega. Se você precisa de um JOIN entre fontes, isso é intermediate.

Exemplo — stg_lgbt_total_casamentos_uf.sql

with origem as (
    select * from {{ source('raw_lgbt', 'raw_lgbt_total_casamentos_uf') }}
)
select
    cod_uf::int                                   as uf_codigo,
    uf                                            as uf_sigla,
    unid_da_federacao                             as uf_nome,
    ano_de_referencia::int                        as ano_referencia,
    total_de_casam_entre_conj_masc_e_fem::bigint  as qtd_casamentos_masc_fem,
    total_de_casam_lesbohomoafetivos::bigint      as qtd_casamentos_lesbohomoafetivos
from origem

grão: 1 linha por UF · vira a view dev_staging.stg_lgbt_total_casamentos_uf

07Camada 2 — Intermediate

models/intermediate/lgbt/int_lgbt_*.sql — aqui mora o cálculo.

Há um modelo por (sub)seção do relatório: int_lgbt_1_populacao, int_lgbt_2_5_casamentos_registro_civil, int_lgbt_7_1_denuncias_ondh… Cada um lê um ou mais stg_lgbt_* (e os seeds), aplica as fórmulas do documento de cálculo da equipe, e devolve todo mundo no mesmo formato — o "contrato longo":

ColunaConteúdo
nivelnacional | estadual | municipal
recorte_codigonull (nacional) · código IBGE da UF (estadual) · do município (municipal)
recorte_nomeBrasil · nome da UF · nome do município
secao / secao_nomenúmero e nome da (sub)seção
indicadorslug estável (ex.: pct_casamentos_lesbohomoafetivos)
categoriaquebra dentro do indicador (ex.: 2023, Negra) — null se não houver
valornumérico
valor_tiponumero_absoluto | percentual | variacao_percentual
ano_referenciaano do dado

Como todos os int_lgbt_* têm exatamente essas colunas, o mart só precisa empilhar (union all).

Padrões de SQL que se repetem aqui

  • with … as (…) (CTEs) em cadeia — cada passo do cálculo é uma CTE nomeada. Lê-se de cima para baixo.
  • cross join lateral (values …) — para "desvirar" colunas: a planilha traz um ano por coluna (2013, 2014…), e isso vira uma linha por ano.
  • union all por nível — o mesmo cálculo agregado 3 vezes (sem group by recorte = nacional; por UF = estadual; por município = municipal).
  • macros para o que repetiria — sobretudo calcula_percentual().

Sub-modelos auxiliares da 6.1

A seção 6.1 tem cinco int_lgbt_*_por_municipio (PAEFI, CREAS×2, Centros POP, acolhimento) que fazem a agregação municipal fina. O int_lgbt_6_1_protecao_social_especial reagrupa esses cinco nos 3 níveis e devolve no contrato longo. É a única seção com essa camada extra — herança do piloto.

08Camada 3 — Marts

models/marts/lgbt/ — o que a aplicação consulta.

lgbt_indicadores.sql — a união

Literalmente empilha todos os intermediate:

select * from {{ ref('int_lgbt_5_1_servicos_saude_trans') }}
union all
select * from {{ ref('int_lgbt_1_populacao') }}
union all
select * from {{ ref('int_lgbt_2_5_casamentos_registro_civil') }}
-- … mais 10 …

Resultado: ~595 mil linhas, 73 indicadores, os 3 níveis, materializado como tabela no schema dev_marts.

As 3 tabelas por nível

lgbt_indicadores_nacional, _estadual, _municipal — cada uma é um recorte fino do mart longo, com as colunas de recorte renomeadas (recorte_codigo → uf_codigo / municipio_codigo_ibge). São table também, porque é o que entra no dump da entrega.

_lgbt_indicadores__schema.yml — testes e descrição

Declara o grão (teste dbt_utils.unique_combination_of_columns), o not_null das colunas-chave, os accepted_values de nivel e valor_tipo, e a descrição de cada coluna (vira a doc gerada).

09Macros

transform/macros/ — SQL reutilizável, compartilhável entre temas.

MacroPara quê
calcula_percentual(num, den, casas=2, sem_denominador=0)Percentual arredondado e protegido contra divisão por zero. Denominador 0 ou nulo → devolve 0 ("sem casos" = 0%). Indicadores de variação passam sem_denominador='null'.
codigo_num(col)Converte código de UF/IBGE para int com segurança — o Excel manda "33", "33.0", e às vezes um hash de anonimização (denúncias do exterior). Não-numérico → NULL.
orientacao_canonica(col)Padroniza rótulo de orientação sexual ("Heterosexual" vs "Heterossexual", "gay" → "Homossexual"…).
ondh_breakdown_percentual(...)Gera a quebra percentual de um indicador ONDH; denominador = soma das categorias do par.
sinan_breakdown_percentual(...)Idem para SINAN; denominador = uma coluna de total explícita.
 
{% macro calcula_percentual(numerador, denominador, casas_decimais=2, sem_denominador=0) %}
    case
        when {{ denominador }} is null or {{ denominador }} = 0 then {{ sem_denominador }}
        else round(100.0 * {{ numerador }} / {{ denominador }}, {{ casas_decimais }})
    end
{% endmacro %}

no modelo: {{ calcula_percentual('lesbo', 'masc_fem') }} → vira o CASE inteiro

10Testes

A rede de segurança. Rodam junto com dbt build.

De schema — em _lgbt_indicadores__schema.yml

Garantem a forma da tabela: nenhum indicador nulo, combinação (nivel, recorte, secao, indicador, categoria, ano) única, valor_tipo só com os 3 valores aceitos, etc.

Singulares — os 12 arquivos em tests/

Cada um compara o valor calculado pelo nosso pipeline com o valor da planilha de cálculo da equipe (o "golden value", escrito na mão no teste). Se divergir, o teste devolve a linha e o build falha.

with esperado (indicador, categoria, valor) as (
    values
        ('estabelecimentos_total',           null,           26),
        ('estabelecimentos_por_habilitacao', 'Ambulatorial', 16),
        ('estados_sem_servico',              null,           12)
),
obtido as (
    select indicador, categoria, valor from {{ ref('lgbt_indicadores') }}
    where nivel = 'nacional' and secao = '5.1'
)
select e.indicador, e.valor as esperado, o.valor as obtido
from esperado e
left join obtido o on o.indicador = e.indicador
                   and o.categoria is not distinct from e.categoria
where o.valor is null or o.valor <> e.valor          -- devolve linha = falhou

Consequência prática

Numa carga de dados nova, esses testes vão falhar de propósito até alguém atualizar os golden values contra as novas planilhas de cálculo. É o comportamento desejado — é assim que você percebe que um número mudou.

11Seeds

transform/seeds/ — carregados com dbt seed.

  • dim_municipio.csv — 5.597 municípios: código IBGE (7 e 6 dígitos), nome, código da UF. É a fonte de verdade do nome do município — os modelos não confiam no nome que vem do Excel (grafias inconsistentes: "Belem"/"Belém").
  • dim_uf.csv — 27 UFs: código, sigla, nome, região.

Viram dev_referencia.dim_municipio / dim_uf e são referenciados com {{ ref('dim_municipio') }} como qualquer modelo.

12Rastreando um indicador de ponta a ponta

Um número — pct_casamentos_lesbohomoafetivos de São Paulo = 1,85% — do Excel ao SELECT do dev.

Planilha

LGBTQIA+ · Perfil PNS · aba "Total_Casamentos_UF"

Uma linha por UF com Total de casamentos entre cônjuges masculino e feminino e Total de Casamentos Lesbohomoafetivos. Para SP: 230.935 e 4.268.

Ingestão → schema raw

python ingest.py → raw.lgbt_perfil_pns_est_reg_civil_total_casamentos_uf

Cópia fiel da aba. Colunas com nomes normalizados/truncados: total_de_casam_entre_conj_masc_e_fem, total_de_casam_lesbohomoafetivos. Tudo como texto/double.

Source declarado

models/staging/lgbt/_lgbt__sources.yml

name: raw_lgbt_total_casamentos_uf (apelido estável) → identifier: a tabela real acima.

Camada 1 — staging

stg_lgbt_total_casamentos_uf.sql → view dev_staging.stg_lgbt_total_casamentos_uf

Renomeia e tipa: cod_uf::int as uf_codigo, …lesbohomoafetivos::bigint as qtd_casamentos_lesbohomoafetivos. Nenhuma conta.

Camada 2 — intermediate

int_lgbt_2_5_casamentos_registro_civil.sql

CTE lesbo lê o staging e monta as linhas por nível. Para o estadual, uma linha por UF com lesbo e masc_fem. O percentual sai da macro:

select 'estadual', uf_codigo,
       {{ calcula_percentual('lesbo', 'masc_fem') }} as valor,
       'percentual' as valor_tipo, 2022 as ano_referencia
from lesbo
-- SP: round(100.0 * 4268 / 230935, 2) = 1.85

Sai no contrato longo: nivel=estadual, recorte_codigo=35, indicador='pct_casamentos_lesbohomoafetivos', categoria=null, valor=1.85.

Camada 3 — mart

lgbt_indicadores.sql (union all) → dev_marts.lgbt_indicadores

A linha entra na pilha junto com as dos outros 72 indicadores. Depois lgbt_indicadores_estadual a expõe com recorte_codigo renomeado para uf_codigo.

Dicionário

docs/lgbt/dicionario-lgbt_indicadores.csv

Uma linha descreve a chave: pct_casamentos_lesbohomoafetivos · sem quebra · percentual · N/E · 2022 · "casamentos lesbohomoafetivos como % dos casamentos masc-fem".

A aplicação

query do dev

select indicador, categoria, valor, valor_tipo, ano_referencia
from lgbt_indicadores_estadual
where uf_codigo = 35;
-- … pct_casamentos_lesbohomoafetivos | (null) | 1.85 | percentual | 2022 …

Vira mapa["pct_casamentos_lesbohomoafetivos"] = 1.85 e o template do relatório faz o bind.

Ver isso no dbt

dbt docs generate && dbt docs serve abre um site com o grafo (DAG) clicável — dá para navegar exatamente essa cadeia de ref() em ref(), ver o SQL compilado de cada modelo e as descrições de coluna.

13Como rodar

Um ciclo completo, na ordem.

# 0. planilhas do ciclo em ingestion/input/lgbt/<ano>/

# 1. ingestão (Python) — recria o schema raw
python ingestion/ingest.py --tema lgbt --ano 2026

# 2. transformação (dbt) — sempre a partir de transform/
cd transform
dbt deps                       # baixa dbt_utils (1x, ou quando packages.yml muda)
dbt seed                       # carrega dim_municipio / dim_uf
dbt build --select tag:lgbt    # roda staging→intermediate→marts + TODOS os testes

# 3. conferir o grafo e a doc
dbt docs generate && dbt docs serve

# 4. gerar o pacote de entrega
python ../scripts/gera_dicionario_lgbt.py
../scripts/exporta_entrega_lgbt.sh
ComandoFaz
dbt runCria/atualiza as views e tabelas dos modelos. Não roda teste.
dbt testSó os testes, contra o que já está no banco.
dbt buildseed + run + test + snapshot, na ordem do DAG. É o que você usa no dia a dia.
dbt build --select tag:lgbtSó os nós com a tag lgbt (56 hoje).
--select stg_lgbt_paefi+Um modelo e tudo que depende dele (o + à direita). +modelo = ele e os ancestrais.
dbt compileGera o SQL final (com ref/macros resolvidos) em target/compiled/ sem rodar.

14A entrega

Formato longo + dicionário. Decidido em setembro/2026.

A aplicação recebe as 3 tabelas por nível como estão (formato longo, ~9 colunas) — não uma tabela larga pivotada. O dev roda uma query por relatório, monta um mapa chave → valor e faz o bind no template.

  • Por que longo: indicador novo no relatório = linha nova, não coluna nova. O schema do banco nunca muda; nada de ALTER TABLE coordenado entre os dois lados.
  • scripts/exporta_entrega_lgbt.sh → 3 .sql (CREATE TABLE + COPY, sem schema/owner), _schema.sql, MANIFEST.txt (contagem + md5), o dicionário e o guia de consumo.
  • scripts/gera_dicionario_lgbt.py → dicionario-lgbt_indicadores.csv: uma linha por indicador (chave de bind, categorias, tipo, unidade, níveis, ano, descrição).
  • Detalhe da entrega e receita de bind: docs/lgbt/consumo-lgbt_indicadores.md.

15Glossário

modeloUm .sql com um SELECT. O dbt o materializa como view ou table.
sourceTabela que o dbt não criou (as raw), declarada em YAML e referenciada com {{ source() }}.
seedCSV do repo carregado como tabela por dbt seed.
ref{{ ref('x') }} — referência a outro modelo; constrói o DAG.
DAG / lineageGrafo de dependências entre modelos. O dbt deriva a ordem de execução dele.
materializaçãoComo o modelo vira objeto no banco: view, table, incremental, ephemeral. Aqui só view e table.
staging / intermediate / martsAs 3 camadas convencionais: limpeza / cálculo / entrega.
macroFunção Jinja que devolve um trecho de SQL. Fica em macros/.
tagRótulo de modelo para seleção (--select tag:lgbt).
teste de schemaRegra declarada em YAML (not_null, unique…).
teste singular.sql em tests/ que passa quando devolve zero linhas.
targetAmbiente do profiles.yml (aqui dev) — define conexão e prefixo de schema.
grãoO que uma linha da tabela representa (ex.: "1 linha por UF").
formato longoUma linha por indicador/categoria, em vez de uma coluna por indicador.
